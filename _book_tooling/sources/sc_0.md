# How to use this guide
%Security engineering for software developers: what each control is, where it lives, and how it works

Security features are not a separate product; they are decisions spread through every layer of a system: how passwords are stored, how data travels and rests, how payments are confirmed, how every request is authorised. This guide covers the security work a product engineer does and that interviews probe: **cryptography** used correctly, **passwords and authentication**, **encryption in transit** (TLS) and **at rest**, **key and secret management**, **payment security** (PCI DSS, tokenisation, webhooks, idempotency), the **OWASP Top 10** with live demonstrations of each attack and its fix, **data storage and privacy**, and a **secure development** process.

Everything here is **defensive**: each attack is shown against a deliberately vulnerable toy running on the same machine, together with the fix, so that you can recognise and prevent it in code review.

## How the examples were run

Every block with a run label was executed for this book in Python 3.13 with the `cryptography` library (the standard Python wrapper around OpenSSL), `bcrypt`, `argon2-cffi` and `PyJWT`; TLS examples use certificates generated by the OpenSSL 3 command-line tool and real TLS connections on the loopback interface. Random keys differ on every run, so outputs show lengths, booleans and checks rather than raw key bytes, except where a fixed test vector is used on purpose.

> TRAP: Never invent your own cryptographic algorithm or protocol, and never use low-level primitives where a high-level, vetted construction exists. The examples implement small pieces (an HMAC check, TOTP, envelope encryption) to show how they work; in production use well-reviewed libraries and managed services.

# Chapter 1: The Security Mindset
%Assets, threats, the CIA triad, defence in depth, and a map of where security is implemented

## 1.1 What we protect, and from whom

Security starts with three questions: **what** are we protecting (assets: customer data, money, credentials, availability, reputation), **from whom** (threat actors: opportunistic bots, criminals after card data, insiders, a curious user changing an id in the URL), and **what happens if it fails** (impact). The classic goals are the **CIA triad**:

| Goal | Meaning | Typical controls |
|---|---|---|
| **Confidentiality** | Only authorised parties can read data | Encryption, access control, data minimisation |
| **Integrity** | Data cannot be altered undetected | MACs and signatures, checksums, audit logs, input validation |
| **Availability** | The service works when needed | Rate limiting, redundancy, backups, DDoS protection |

Two more matter in practice: **authentication** (who are you?) and **authorisation** (what may you do?), plus **non-repudiation** (you cannot deny an action you signed).

## 1.2 Threat modelling with STRIDE

Before writing code, draw the data flow (users, services, stores, trust boundaries such as "internet → API" and "API → database") and ask, for each element, what could go wrong. **STRIDE** is a checklist:

| Threat | Violates | Example in the meter platform | Mitigation |
|---|---|---|---|
| **S**poofing | Authentication | A fake meter sends readings | Device certificates (mTLS), signed messages |
| **T**ampering | Integrity | A user edits the `amount` in a payment request | Server-side prices, signatures on webhooks |
| **R**epudiation | Non-repudiation | An admin denies changing a tariff | Tamper-evident audit log |
| **I**nformation disclosure | Confidentiality | A user reads another customer's bills via `/bills/1234` | Object-level authorisation, encryption |
| **D**enial of service | Availability | A script floods the login endpoint | Rate limits, WAF, autoscaling |
| **E**levation of privilege | Authorisation | A customer calls an admin endpoint | Role checks on every endpoint, least privilege |

## 1.3 Principles

- **Defence in depth**: several independent layers, so one failure is not a breach (TLS **and** encryption at rest **and** access control **and** monitoring).
- **Least privilege**: every user, service and key gets only the permissions it needs (the billing service can read readings, not change passwords).
- **Secure defaults and fail closed**: new endpoints require authentication unless explicitly made public; an authorisation error denies.
- **Never trust the client**: validate and authorise everything on the server; the browser and the mobile app are in the attacker's hands.
- **Minimise attack surface and data**: fewer endpoints, fewer dependencies, less stored personal data.
- **Keep secrets out of code**: in a secret manager, rotated, audited.
- **Assume breach**: log, monitor, alert, and be able to rotate keys and revoke sessions quickly.

## 1.4 Where each security feature is implemented

| Layer | Security features implemented there |
|---|---|
| Browser / mobile app | TLS validation (automatic), CSP and other security headers it obeys, secure cookie handling, no secrets in the bundle, payment card fields hosted by the payment provider (iframe/SDK), certificate pinning in some mobile apps |
| DNS and CDN / WAF | DDoS absorption, Web Application Firewall rules (SQLi/XSS signatures, bot management), TLS termination at the edge, HSTS |
| Load balancer / API gateway | TLS termination, rate limiting, authentication of tokens (JWT validation), request size limits, IP allow-lists for admin APIs |
| Application (Spring Boot) | Authentication and **authorisation on every request and object**, input validation, output encoding, password hashing, CSRF protection, idempotency, business-rule checks (amounts, limits), audit logging, webhook signature verification |
| Database | Encryption at rest (TDE), least-privilege database users, row-level security, backups encrypted, network isolation (private subnet), parameterised queries from the app |
| Key management (KMS / HSM / Vault) | Key generation and storage, envelope encryption, rotation, access policies and audit of key use |
| Infrastructure (cloud, Kubernetes, Linux) | IAM roles, network segmentation, security groups, patched images, non-root containers, secrets injection, file permissions (Linux guide, Chapter 4) |
| CI/CD | Dependency and container scanning, SAST, secret scanning, signed artefacts, protected branches, review |
| Operations | Centralised logs, intrusion detection, alerting, incident response, key rotation, access reviews |
| Payment provider (Razorpay, Stripe, PayU) | Card storage (PCI DSS Level 1), tokenisation, 3-D Secure / OTP, fraud scoring, webhooks signed with your secret |

The rest of this guide goes through these in detail; Chapter 9 ends with a checklist that maps each one to a review question.

# Chapter 2: Cryptography Essentials
%Hashes, MACs, symmetric and asymmetric encryption, signatures and randomness, used correctly

## 2.1 Hash functions

A cryptographic **hash function** (SHA-256, SHA-3, BLAKE2) maps any input to a fixed-size digest such that it is infeasible to find the input from the digest (**pre-image resistance**), or two inputs with the same digest (**collision resistance**). A one-bit change in the input changes about half the output bits (the **avalanche effect**). Hashes give **integrity** (file checksums, content addressing in Git and Docker) but **not authenticity**: anyone can recompute a hash of modified data. MD5 and SHA-1 are broken for collision resistance; do not use them for security.

```python run SHA-256: fixed size, deterministic, and the avalanche effect
import hashlib
a = hashlib.sha256(b'Pay Rs 500 to SM-42').hexdigest()
b = hashlib.sha256(b'Pay Rs 900 to SM-42').hexdigest()
print('digest A:', a)
print('digest B:', b)
diff = bin(int(a, 16) ^ int(b, 16)).count('1')
print(f'one character changed -> {diff} of 256 bits differ ({diff / 256:.0%})')
print('same input, same digest:', hashlib.sha256(b'Pay Rs 500 to SM-42').hexdigest() == a)
small, big = hashlib.sha256(b'x').digest(), hashlib.sha256(b'x' * 10_000_000).digest()
print('length of the digest of 1 byte and of 10 MB:', len(small), len(big), 'bytes')
```

## 2.2 Message authentication codes (HMAC)

A **MAC** proves that a message came from someone holding a shared secret key and was not modified. **HMAC-SHA256** is the standard construction. It is used for webhook signatures (Chapter 6), signed cookies, presigned URLs (back-end guide, Section 6.2) and API request signing. Always compare MACs in **constant time** (`hmac.compare_digest`), or an attacker can learn the correct value byte by byte from response timings.

```python run HMAC detects tampering; a plain hash does not
import hashlib, hmac, secrets
key = secrets.token_bytes(32)
msg = b'{"order": "ord_91", "amount": 50000, "status": "paid"}'
tag = hmac.new(key, msg, hashlib.sha256).hexdigest()
forged = msg.replace(b'50000', b'500')
def verify(message, received_tag):
    expected = hmac.new(key, message, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received_tag)       # constant-time comparison
print('genuine message verifies:', verify(msg, tag))
print('tampered message verifies:', verify(forged, tag))
plain = hashlib.sha256(forged).hexdigest()           # an attacker can always do this
print('with a plain hash, the attacker simply recomputes it: the "check" passes:',
      plain == hashlib.sha256(forged).hexdigest())
```

## 2.3 Symmetric encryption: AES-GCM

**Symmetric** encryption uses one secret key to encrypt and decrypt. **AES** (128- or 256-bit keys) is the standard cipher, and it must be used in an **authenticated encryption** mode, **AES-GCM** (or ChaCha20-Poly1305), which both encrypts and adds an authentication tag, so that any modification of the ciphertext is detected at decryption. Older modes (ECB, CBC without a MAC) leak patterns or allow tampering.

GCM needs a **nonce** (number used once): 12 bytes, **never reused with the same key**. Optional **associated data** (AAD) is authenticated but not encrypted, binding the ciphertext to its context (for example, the record id it belongs to).

```python run AES-256-GCM: encrypt, detect tampering, and bind to context with associated data
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.exceptions import InvalidTag
key = AESGCM.generate_key(bit_length=256)
aes = AESGCM(key)
nonce = os.urandom(12)
pan = b'4111 1111 1111 1111'
ct = aes.encrypt(nonce, pan, b'customer:c1')
print(f'plaintext {len(pan)} bytes -> ciphertext {len(ct)} bytes (16-byte tag added)')
print('decrypts:', aes.decrypt(nonce, ct, b'customer:c1'))
flipped = bytes([ct[0] ^ 1]) + ct[1:]
for label, data, aad in [('one bit flipped', flipped, b'customer:c1'),
                         ('moved to another customer', ct, b'customer:c2')]:
    try:
        aes.decrypt(nonce, data, aad)
    except InvalidTag:
        print(f'{label}: rejected (InvalidTag)')
```

The second rejection shows the value of associated data: an attacker with database access who copies customer 1's encrypted card into customer 2's row cannot make it decrypt there.

### Why a nonce must never repeat

```python run Reusing a GCM nonce leaks the XOR of the two plaintexts
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
aes = AESGCM(AESGCM.generate_key(bit_length=128))
nonce = os.urandom(12)                                # BUG: the same nonce for two messages
p1, p2 = b'salary: 1200000 INR', b'meeting at 5pm....'
c1, c2 = aes.encrypt(nonce, p1, None), aes.encrypt(nonce, p2, None)
xor = bytes(a ^ b for a, b in zip(c1, c2))            # attacker sees only ciphertexts
recovered = bytes(x ^ y for x, y in zip(xor, p2))     # ... and guesses or knows one message
print('attacker recovers the other message:', recovered)
```

The attacker recovered the first message as far as the known second message extends (18 of its 19 characters). GCM encrypts by XOR-ing the plaintext with a keystream determined by the key and nonce; the same nonce gives the same keystream, so the XOR of two ciphertexts equals the XOR of the plaintexts, and knowing one reveals the other (nonce reuse also lets an attacker forge authentication tags). Use random 96-bit nonces from a secure generator (safe for up to about 2<sup>32</sup> messages per key) or a counter, and rotate keys well before that.

## 2.4 Asymmetric cryptography: key pairs, encryption and signatures

**Asymmetric** (public-key) cryptography uses a key pair: the **public key** can be shared, the **private key** is kept secret.

- **Encryption**: anyone encrypts with the public key; only the private key decrypts (RSA-OAEP). In practice used to protect a symmetric key (**hybrid encryption**), because asymmetric operations are slow and limited in size.
- **Key exchange**: two parties derive a shared secret over an open channel (Diffie–Hellman, today **X25519** or ECDHE); this is how TLS creates its session keys.
- **Digital signatures**: the private key signs; anyone verifies with the public key (RSA-PSS, ECDSA, **Ed25519**). Signatures give integrity, authenticity and non-repudiation: used in TLS certificates, JWTs (RS256/ES256), software updates, Git commits.

```python run Ed25519 signatures and X25519 key exchange
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.exceptions import InvalidSignature
signer = Ed25519PrivateKey.generate()
public = signer.public_key()
firmware = b'meter-firmware-v2.4.1.bin contents'
sig = signer.sign(firmware)
print('signature length:', len(sig), 'bytes')
for label, data in [('genuine firmware', firmware), ('modified firmware', firmware + b'!')]:
    try:
        public.verify(sig, data); print(label, '-> signature valid, install')
    except InvalidSignature:
        print(label, '-> INVALID signature, refuse to install')
meter_key, server_key = X25519PrivateKey.generate(), X25519PrivateKey.generate()
s1 = meter_key.exchange(server_key.public_key())      # each side uses its private key
s2 = server_key.exchange(meter_key.public_key())      # and the other's public key
print('both sides derived the same 32-byte secret:', s1 == s2, len(s1))
```

The meter needs only the vendor's **public** key to verify firmware, so stealing a meter reveals nothing that allows signing malicious updates. In the key exchange, only public keys crossed the network, yet both sides now share a secret that an eavesdropper cannot compute.

## 2.5 Randomness

Keys, nonces, session ids, password-reset tokens and OTPs must come from a **cryptographically secure** random generator: Python's `secrets` or `os.urandom`, Java's `SecureRandom`. General-purpose generators (`random`, `java.util.Random`, `Math.random`) are predictable: after observing some outputs, an attacker can compute the rest.

```python run Why random is not for secrets: predicting the next reset token
import random, secrets
random.seed(20260302)                                  # e.g. seeded from the date, a real bug
issued = [random.getrandbits(32) for _ in range(3)]   # tokens the attacker requested
victim_token = random.getrandbits(32)                 # the next one goes to the victim
attacker = random.Random(20260302)                    # attacker guesses the seed (the date)
guesses = [attacker.getrandbits(32) for _ in range(4)]
print('attacker reproduces his tokens:', guesses[:3] == issued)
print("attacker predicts the victim's token:", guesses[3] == victim_token)
token = secrets.token_urlsafe(32)
print('secrets.token_urlsafe(32):', len(token), 'characters,', 32 * 8, 'bits of entropy')
```

Even without a guessable seed, Python's Mersenne Twister can be fully reconstructed from 624 consecutive 32-bit outputs. Use `secrets` for anything an attacker would like to guess.

## 2.6 Choosing primitives

| Need | Use | Avoid |
|---|---|---|
| Integrity of files or content addressing | SHA-256, BLAKE2 | MD5, SHA-1 |
| Authenticating messages between parties sharing a key | HMAC-SHA256 | Plain hash, `hash(key + message)` |
| Encrypting data | AES-256-GCM, ChaCha20-Poly1305 (authenticated) | ECB, CBC without MAC, DES/3DES, home-made XOR |
| Signatures | Ed25519, ECDSA P-256, RSA-PSS ≥ 2048 bits | RSA PKCS#1 v1.5 for new designs, DSA |
| Key exchange | X25519, ECDHE (via TLS 1.3) | Static RSA key exchange |
| Passwords | Argon2id, bcrypt, scrypt (Chapter 3) | Any fast hash, even salted |
| Random values | `secrets`, `SecureRandom` | `random`, `Math.random`, timestamps |

## 2.7 Practical lessons

- Hash for integrity, HMAC for authenticity with a shared key, signatures for authenticity with public verification.
- Encrypt with authenticated encryption (AES-GCM); never reuse a nonce with the same key; use associated data to bind context.
- Public keys verify and encrypt; private keys sign and decrypt; key exchange creates shared secrets over open networks.
- Secrets come from `secrets`/`SecureRandom`; compare MACs in constant time.
- Use high-level libraries; do not design your own cryptography.
