# Hints
%A nudge for each exercise; the worked answers follow in the solutions

## Part 1 hints

| Exercise | Hint |
|---|---|
| G1.1 | Think scope, autonomy and multiplier behaviours, not more of the same tasks |
| G1.2 | High output but negative leverage: are the two juniors better off? |
| G1.3 | Compare total team output, not individual commits |
| G1.4 | Depth earns trust; breadth enables design; pair and read outside your area |
| G1.5 | Code is read far more than written; cleverness is a tax on every future reader |

## Part 2 hints

| Exercise | Hint |
|---|---|
| G2.1 | Style should be automated; blocking on preferences; teach, praise, prioritise |
| G2.2 | Evidence, steelman, then disagree-and-commit unless it is a one-way door |
| G2.3 | Context, goals/non-goals, requirements, design, alternatives, trade-offs, rollout |
| G2.4 | Scale now and in 2 years, team expertise, operability, cost, reversibility |
| G2.5 | Sort by reversal cost × chance of being wrong |
| G2.6 | YAGNI: four types, twice a year; build the simple thing, revisit if it changes |

## Part 3 hints

| Exercise | Hint |
|---|---|
| G3.1 | Coverage is a weak proxy; target confidence and risk, test behaviour |
| G3.2 | Retries hide real races and erode trust in the whole suite |
| G3.3 | 99.99% ≈ 53 min/year; staff, working hours only — overkill |
| G3.4 | SLI, burn-rate alerts, freeze features when exhausted |
| G3.5 | Mitigate first: roll back the recent deploy; diagnose after users are safe |
| G3.6 | The system let it happen; ask why, not who; guardrails not approvals |

## Part 4 hints

| Exercise | Hint |
|---|---|
| G4.1 | Amdahl: attack the 60%; even instant, the ceiling is 1/(1−0.6) |
| G4.2 | N+1 across the network; batch, parallelise, cache; prefer batch |
| G4.3 | Egress, orphaned resources, a runaway job, logging volume, a new feature |
| G4.4 | Model the compounding drag; tie refactor to the next feature in that module |
| G4.5 | Add new column, dual-write, backfill, verify, switch reads, drop old |

## Part 5 hints

| Exercise | Hint |
|---|---|
| G5.1 | Translate to their goal: speed, reliability, cost, churn — not internals |
| G5.2 | Bottom line up front; cut the build-up |
| G5.3 | Prototype, shared goal, make it easy to adopt, win over one team first |
| G5.4 | You are robbing their growth and becoming a bottleneck; teach, don't fix |
| G5.5 | The team lacks psychological safety; fix the environment, not the person |
| G5.6 | Reframe to the shared goal and the data; decide, then disagree-and-commit |
| G5.7 | Now, to your manager and stakeholders; early bad news is manageable |

## Part 6 hints

| Exercise | Hint |
|---|---|
| G6.1 | Depth = where you solve the hardest problems; breadth = what you can design across |
| G6.2 | Get specific criteria from your manager; gather evidence; sponsors; set a horizon |
| G6.3 | Leadership, conflict, failure, mentoring, a hard decision, influence |
| G6.4 | Clarify requirements, estimate scale, name the core API, state assumptions |
| G6.5 | Fundamentals and transferable skills are durable; specific tools perish |
| G6.6 | Say no with the trade-off; redirect, teach, or time-box; protect focus |
| G6.7 | Systems over willpower: boundaries, delegation, automation, real rest |
